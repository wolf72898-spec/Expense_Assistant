## 三、基座能力深度核验（已读完源码，不是看 README 下的判断）

代码量 4,849 行 Python，依赖极轻（`pyyaml` 必需，`jsonschema`/`pypdf` 推荐）。

### 3.1 规则完全数据驱动 —— 直接支撑"制度维护"

```
lib/expense-report-package/config/policy.default.json   公司层制度（类目/必备字段/必备证据/限额）
lib/expense-report-prep/ontology/rbox/core.yaml         国标层规则（GB/T 42965 票据要素）
company/policy.json                                     企业制度包（示例科技有限公司）
```

制度不是写死在代码里的，而是 **JSON/YAML + JSON Schema 校验**。例：

```json
"lodging": {
  "label": "住宿",
  "required_fields": ["trip.city", "trip.check_in", "trip.check_out"],
  "required_evidence": [["e_invoice", "invoice"], ["hotel_folio"]],
  "cap": { "amount": 500, "per": "night",
           "by_city": { "北京": 800, "上海": 800, "深圳": 700 }, "mode": "clip" }
}
```

→ 你要的"制度维护"，本质就是在这一层之上加 **版本管理 + 生效期 + 审批发布 + 变更留痕**。

### 3.2 字段级溯源 —— "业务事实核对"的核心武器

`FieldProvenance.method` 枚举已定义 8 种取值：

```
xml | ofd_structured | pdf_text | ocr | user_stated | inferred | policy_default | user_confirmed
```

**每个字段都带来源标签和置信度。** 这意味着系统天然能区分：
- `xml` / `ofd_structured` → 权威事实，可直接采信
- `ocr` / `inferred` → 机器推测，**必须人工确认**
- `user_confirmed` → **财务助手已核对**

这正是"业务事实由财务助手核对"在数据结构层面的落点：
> **凡 provenance ≠ 权威来源 的字段，一律不准进付款结论，必须过财务复核转为 `user_confirmed`。**

### 3.3 置信度门控 —— HITL 已有骨架

`jev_rbox.py` 中 AI 判定分三档：

| 档位 | 含义 | 处理 |
|---|---|---|
| `auto` | 置信度 ≥ 上限 | 直接采信 |
| `confirm` | 介于中间 | 向员工确认 |
| `escalate` | < 下限 | 交人工处理 |

→ 扩展一个 `finance` 档位（强制升级到财务岗），即为财务复核流程。

### 3.4 已有模型可直接复用

| 模型 | 已有定义 | 对需求的支撑 |
|---|---|---|
| `ReportStatus` | `draft / incomplete / ready / submitted` | 单据状态（需扩展审批/付款态） |
| `TraceEvent.actor` | `agent / user / system` | 审计留痕（需加 `finance` 角色） |
| `Gap.type` | 20 种：invoice_verification、invoice_status、duplicate_suspect、policy_limit… | 核对项清单 |
| `Source` | file/folder/utterance/system + sha256 | 证据固化 |

## 四、四项需求 → 基座映射

| # | 你的需求 | 基座已有 | 需要新建 |
|---|---|---|---|
| **A** | 自助查询有效制度 | 制度结构化 + schema + 版本号 | **制度 RAG 问答**：文档切片 → 向量库 → 按「已发布且生效中」版本过滤检索 → 带引用的答案 |
| **B** | 经授权查询本人单据状态 | `ReportStatus` 4 态、report_id | **认证授权层**（SSO/OAuth + 行级 `owner_id = 当前用户`）+ **单据状态适配器**（对接费控/ERP） |
| **C** | 制度维护 | 制度 JSON/YAML + Schema | **制度管理服务**：CRUD、版本树、生效期、审批发布、变更审计 |
| **D** | 业务事实由财务助手核对 | 溯源标签、置信度门控、Gap 引擎、Trace 留痕 | **财务复核工作台**：待核队列、逐字段确认/驳回、复核意见留痕、AI 结论不可作付款依据 |

**一句话设计原则（建议写进项目 README 第一条）：**
> AI 负责引制度、做初判、标来源；**事实认定权与付款决定权归财务岗**。AI 的输出是"建议"，不是"结论"。

这条原则参考了 `auditable-expense-agent` 的理念（"LLM is advisory; policy is law"）——该仓库无 License，只借鉴思想，不引用代码。

## 五、建议的目标架构

```
青禾报销助手_wolf
│
├─ policy-service        制度中枢（新增）
│   ├─ 制度 CRUD / 版本树 / 生效期 / 审批发布
│   ├─ 制度变更审计（谁、何时、改了哪条、依据什么）
│   └─ 编译输出 → 复用基座的 policy.json + core.yaml 格式
│
├─ qa-service            制度问答（新增，对应需求 A）
│   ├─ 制度文档切片 + 向量化（按版本/生效期打标）
│   ├─ 检索时强制过滤 status=published AND effective∈[now]
│   ├─ 答案必须带制度条款引用；检索不到就说"制度未覆盖"
│   └─ 数值计算走确定性工具，禁止 LLM 心算
│
├─ claim-service         单据服务（新增，对应需求 B）
│   ├─ 认证：SSO / 企业微信 OAuth
│   ├─ 授权：行级隔离 owner_id = 当前用户（越权即拒，不返回存在性）
│   └─ 状态适配器：对接青禾现有费控/ERP（无 API 则先做人工同步）
│
├─ review-console        财务复核台（新增，对应需求 D）
│   ├─ 待核队列：provenance ∈ {ocr, inferred} 的字段优先
│   ├─ 逐字段 确认 / 驳回 / 补充证据 → 置为 user_confirmed
│   ├─ TraceEvent 记录 actor=finance
│   └─ 复核未完成的单据，状态不得推进到 payable
│
└─ engine/               规则与凭证内核（复用基座，Apache-2.0）
    ├─ expense_pkg.py    票据解析、Gap 引擎、打包
    ├─ expense_prep.py   SQLite 存储、R-box 编译
    └─ ontology/         core.yaml（国标）+ policy.json（公司）
```

| 阶段 | 目标 | 交付物 |

| **P0** | 基座跑通 + 合规落地 | 引入 `upstream/expense-assistant`，补 `NOTICE`/变更声明，替换为青禾制度包，跑通 `doctor` + 场景测试 |
| **P1** | 制度中枢（需求 C 先行） | 制度管理服务 + 版本/生效期 + 变更审计。**先做 C，因为 A 和 D 都依赖它** |

**依赖顺序说明**：C → A → D → B。制度中枢是所有模块的唯一事实源，必须先立；B 依赖外部系统接口，可并行准备但联调放最后。

## 七、风险提示

1. **基座 star 为 0、仅 1 次提交**（`673580d Expense Assistant 0.3.1: initial open-source release`），无社区验证、无 issue 反馈渠道。核心逻辑需你自己做一遍回归测试（`tests/run_scenarios.py` 已有场景框架可复用）。
2. **示例制度包是虚构的**（`示例科技有限公司`），必须整体替换，不可直接上线。
3. **GB/T 42965 只对齐了要素名称**，标准正文未包含，强合规场景需自行核对标准原文。
4. **基座是 Claude 插件 + CLI 形态**，不含 Web 服务、不含多用户。你要做的是把它"内核化"再包一层服务，这个改造量不小。
5. 建议先做 **P0 冒烟验证**：确认它能正确解析青禾真实数电票 XML/OFD 样本，再决定是否全量投入。
