# 青禾报销助手_wolf · 技术架构设计

> 版本：v0.1（骨架）｜ 2026-10-09
> 交付形态：**企业微信 / 钉钉 机器人**
> 基座：`bonc-ai/expense-assistant` @ `673580d`（Apache-2.0）

---

## 0. 一条总原则

> **AI 负责引制度、做初判、标来源；事实认定权与付款决定权归财务岗。**
> AI 的输出是「建议」，不是「结论」。

这句话不是口号，它在代码里对应三处硬约束：

| 约束 | 落点 |
|---|---|
| 制度未覆盖必须拒答，不许编 | `qa/service.py` → `Answer.escalated` |
| 金额必须由代码算，不许模型心算 | `qa/calculator.py` → `CapCalculator` |
| 未复核完的事实阻断付款 | `review/service.py` → `can_advance_to_payable()` |

## 1. 总体架构

```
   企业微信 / 钉钉
        │  消息 + 已认证的用户身份
        ▼
┌──────────────────────────────────────────────┐
│  bot/router.py   意图路由 + 权限门（第一道）      │
│  规则匹配优先，模型兜底；财务/管理意图先进角色校验   │
└───────────────┬──────────────────────────────┘
                │
     ┌──────────┼──────────┬─────────────┐
     ▼          ▼          ▼             ▼
┌─────────┐ ┌────────┐ ┌────────┐ ┌──────────┐
│ qa/     │ │ claim/ │ │review/ │ │ policy/  │
│ 制度问答 │ │ 单据查询│ │财务复核 │ │ 制度中枢  │
│ 需求 A  │ │ 需求 B │ │ 需求 D │ │ 需求 C   │
└────┬────┘ └───┬────┘ └───┬────┘ └────┬─────┘
     │          │          │           │
     │          │          │     编译为 policy.json
     └──────────┴──────────┴─────┬─────┘
                                 ▼
              ┌──────────────────────────────────┐
              │  engine/  规则与凭证内核（上游）      │
              │  票据解析 · Gap 引擎 · 字段级溯源      │
              │  置信度门控 · 可审计打包              │
              └──────────────────────────────────┘
```

**依赖方向是单向的**：`policy/` 是唯一事实源，`qa/` `review/` 都从它取制度；
`engine/` 只消费 `policy/` 编译产物，不反向依赖。

## 2. 权限模型

| 能力 | employee | finance | admin | 数据范围 |
|---|:--:|:--:|:--:|---|
| 问制度（A） | ✅ | ✅ | ✅ | 全部**已发布且生效中**的条款 |
| 查本人单据（B） | ✅ | ✅ | ✅ | `owner_id = 自己` |
| 查他人单据（B） | ❌ | ✅ | ✅ | 全量，**每次读取留痕** |
| 制度起草 | ❌ | ❌ | ✅ | — |
| 制度审批发布（C） | ❌ | ✅ | ❌ | **审批人 ≠ 起草人** |
| 财务复核（D） | ❌ | ✅ | ❌ | 待核事实队列 |
| 推进付款 | ❌ | ✅ | ❌ | 需全部事实复核完成 |

### 三条安全设计

1. **越权不泄露存在性** —— 查别人的单返回「查无此单」，而非「无权访问」。
   否则可用单号枚举探测全公司报销数据。见 `claim/authz.py`。
2. **过滤下推到存储层** —— `owner_id = ?` 作为查询条件，
   不是查出来再内存过滤（漏写一次就是全量泄露）。
3. **跨人读取必留痕** —— 财务查员工单据写入 `data/audit/claim_access.jsonl`。

## 3. 模块设计

### 3.1 `policy/` 制度中枢（需求 C）—— 已完成

制度的**唯一事实源**。没有它，A 无制度可引、D 无依据可核，所以先做。

- **状态机**：`draft → pending → published → superseded`，非法迁移直接拒绝
- **不可变性**：已发布版本改不了，改制度只能发新版（历史单据可追溯当时的制度）
- **生效期**：旧版 `effective_to` 收敛为「新版生效日的前一天」
  → 2026-02-01 查到 v1，2026-08-01 查到 v2，历史判定不会错乱
- **职责分离**：审批人不得是起草人（代码强制，不是流程约定）
- **字段级 diff**：每次变更记录 `from → to`，审批时看得见改了什么

### 3.2 `qa/` 制度问答（需求 A）—— 骨架完成

- **只检索生效条款**：草稿/待审批/已废止的条款绝不出结果
- **主题词硬门槛**：问题的主题词在条款里一个都没命中 → 判为「制度未覆盖」。
  不加这条，「团建费能报吗」会命中「报销时限」条款，答非所问。
  *财务场景下，错误引用比拒答危害更大。*
- **金额走计算器**：`CapCalculator` 直接读制度 cap 配置，与制度同源
- **越界转人工**：个税、劳动法、薪酬等直接拒绝并指明找谁

当前检索为**词项重叠打分**（零依赖、离线可跑）。
接入向量库只需替换 `qa/retriever.py` 的 `search()`，上层不变。

### 3.3 `claim/` 单据查询（需求 B）—— 骨架完成

- `ClaimAdapter` 抽象接口 + `MockClaimAdapter`（内存，跑通链路）
- `HttpClaimAdapter` 骨架已备：待接入青禾费控/ERP
- 状态在基座 4 态基础上扩展 5 态：`approving / approved / rejected / payable / paid`

> ⚠️ **待你确认**：单据数据到底来自现有费控/ERP，还是本系统自建？
> 这决定 `HttpClaimAdapter` 的实现方式，需要提供接口文档。

### 3.4 `review/` 财务复核（需求 D）—— 骨架完成

技术抓手是基座已有的**字段级溯源**：

| 溯源标签 | 风险等级 | 是否必须人工核 |
|---|:--:|:--:|
| `xml` / `ofd_structured` | 权威 | 否，直接采信 |
| `user_stated` | 员工自述 | 否（抽查） |
| `pdf_text` / `ocr` | 文档抽取 | **是** |
| `inferred` / `policy_default` | 模型推断 | **是**，且不得作为最终依据 |

- 队列按 `风险 = f(来源, 置信度)` 降序，模型推断项排最前
- 确认后溯源标签转为 `finance_confirmed`
- **付款闸门是硬拒绝，不是提示**：有未复核项 → `can_advance_to_payable()` 返回 False

### 3.5 `bot/` IM 入口 —— 骨架完成

- 意图路由**用规则不用模型**：判错会走错权限分支，代价不对等；
  规则可测试、可审计、零成本
- 出现单号（`RPT-2026-0001`）→ 无条件按查状态处理
- 权限门在路由层第一道拦截，不等到业务逻辑
